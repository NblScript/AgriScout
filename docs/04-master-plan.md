# AgriScout 主计划（v1.0）

> 整合：系统蓝图 + 开发路线图 + 调研结论。本文件是项目的唯一权威计划，后续里程碑更新以它为准。

## 1. 项目定义

田间巡检小车每 0.5 米拍照 + 采集天气数据 → 平台自动判断作物生长情况 → 给出可追溯的农事建议，
覆盖作物全生命周期的管理平台。目标用户：农业企业 / 农业技术员（多地块、多人协作）。

## 2. 成功标准

| 阶段 | 时间 | 标准 |
|------|------|------|
| 短期（M0–M6） | 约 3 周 | 用模拟数据在浏览器完整演示"巡田→地图轨迹→每点评估→农事建议" |
| 中期（M7+） | 视硬件 | 真车（任意档次）发出的数据进入平台，平台零改动 |
| 长期 | 持续 | 多季对比、产量预测、标注回流自训模型、LLM 建议/问答 Agent |

## 3. 核心场景（用户视角）

1. 技术员在地图上画出地块边界，登记本季作物（品种、播种日期）
2. 创建巡检任务 → 小车下田（或模拟器一键生成）
3. 巡田完成，平台自动分析每个采样点：生育期、长势等级、病虫害风险
4. 平台汇总天气+分析结果，命中规则库，生成农事建议（可追溯到规则 id）
5. 技术员在地图/时间轴上回看全场，采纳/驳回建议
6. 对识别结果有疑问的照片人工复核 → 标注进入数据集 → 反哺模型训练（数据回流闭环）

## 4. 系统架构（端-边-云）

```
端（小车）   采集+压缩：RGB 照片、天气传感器、NDVI、RTK 坐标
            每 0.5m 触发一个采样点；可选 RK3588 端侧推理（YOLO 轻量模型）
边（网关）   实时推理 + 离线兜底 + 增量学习（"边缘执行-云演进"）
云（平台）   数据接入 API → 分析引擎 → 生长评估 → 规则建议引擎 → 可视化
            标注回流闭环；演进预留：数字孪生/联邦学习/LLM 报告
通信        小数据(天气/状态) LoRa；图像 4G/5G；接入层 HTTP(现在)/MQTT(真车)
```

## 5. 技术栈

| 层 | 选择 | 说明 |
|----|------|------|
| 后端 | Python 3.14 + FastAPI + SQLAlchemy 2 | 接口自动文档、依赖注入 |
| 前端 | Vue 3 + TypeScript + Vite | 地图（Leaflet）+ 图表（ECharts） |
| 数据库 | 开发 SQLite → 生产 PostgreSQL + PostGIS | 空间查询：轨迹、采样点、按区域聚合 |
| 文件 | 本地目录（开发）→ 对象存储（生产） | 照片量大，不存库 |
| 测试 | pytest + httpx | 每里程碑带测试 |
| 部署 | docker-compose | 数据库一键起，后续加前后端容器 |

## 6. 数据模型（v1.0 详细字段）

| 实体 | 关键字段 | 说明 |
|------|----------|------|
| User | username, password_hash, role(admin/technician) | 权限分角色 |
| Field | name, boundary(GeoJSON多边形), area_ha, soil_type | 地块边界与属性 |
| Crop | name, variety, lifecycle_days, stages(JSON:各生育期天数), default_rules | 作物生命周期参数 |
| Planting | field_id, crop_id, sowing_date, expected_harvest_date, status | 地块×作物×批次 |
| Device | code, name, type(rover/drone/station), model, status | 载体抽象：小车/无人机/固定点都是数据源 |
| Patrol | field_id, planting_id, device_id, started_at, ended_at, track(LineString), status | 一次巡检任务 |
| CapturePoint | patrol_id, seq, distance_m, geom(Point), captured_at, photo_url | 每 0.5m 一个点（一等公民） |
| WeatherSample | capture_point_id, patrol_id, temp_c, humidity_pct, light_lux, wind_mps, rain_mm, soil_temp_c, soil_moisture_pct | 天气快照+时序 |
| Analysis | capture_point_id, analyzer_version, growth_stage(JSON概率), vigor_level(1-5), ndvi, disease_detections(JSON), risk_score | 每个点的评估结果 |
| Advice | patrol_id, capture_point_id, rule_id, content, priority, status(suggested/accepted/rejected) | 可追溯建议 |
| Rule | rule_key, crop_id, condition(JSON), action, priority, active | 规则库，可配置 |
| Annotation | capture_point_id, user_id, label, bbox, reviewed_at | 人工复核→数据集（回流闭环） |

## 7. 关键接口契约（提前定死）

### 7.1 数据接入协议（采集端↔平台，JSON 巡检包）
```json
{
  "patrol": { "field_id": 1, "device": "sim-001",
              "started_at": "...", "ended_at": "...", "track": [[lng,lat],...] },
  "capture_points": [
    { "seq": 12, "distance_m": 6.0, "lng": ..., "lat": ..., "captured_at": "...",
      "photo": "<base64或URL>",
      "weather": { "temp_c": 26.3, "humidity_pct": 68, "light_lux": 42000,
                   "wind_mps": 1.2, "rain_mm": 0.0 } }
  ]
}
```
平台不关心 device 是模拟器还是真车。

### 7.2 图像识别接口（分析管线内部）
```python
class Analyzer(Protocol):
    def analyze(self, image: bytes, context: CaptureContext) -> AnalysisResult: ...
```
占位实现（M3）→ YOLOv8（P3）→ 自训+端侧量化（后期），业务层零改动。

### 7.3 建议规则格式（YAML，M4）
```yaml
- id: R-WHEAT-DROUGHT-01
  crop: 小麦
  condition: { stage: 拔节期, rain_7d_mm: { lt: 5 } }
  action: 建议灌溉，亩灌水量 40–50 方
  priority: high
```

## 8. AI 能力路线（小模型识别 + 大模型建议）

### 8.1 识别线（YOLO 小模型，车上跑）
| 级别 | 方案 | 时机 |
|------|------|------|
| L0 | 占位规则：绿色覆盖率/颜色统计估长势 | M3（立即） |
| L1 | 预训练 YOLOv8n/s 微调，先部署在云端 | P3（有真实照片） |
| L2 | 自训数据集 + 端侧部署（RK3588 量化，参考 YOLOv8Ghost 7.7ms/张、86.73%） | 数据积累后 |
| 支撑 | 标注回流闭环：复核界面 + Annotation 表 + 数据集导出 | M6 起持续 |

### 8.2 建议线（LLM 大模型，云端跑）
| 级别 | 方案 | 时机 |
|------|------|------|
| L0 | 规则引擎：作物×阶段×天气→固定建议，可追溯 | M4（立即） |
| L1 | 规则兜底 + LLM 生成自然语言解释/报告 | M6 后 |
| L2 | 诊断/问答 Agent（"3号地块长势为何下降？"） | 远期 |

## 9. 硬件路线（不阻塞软件）

| 档位 | 配置 | 成本 | 用途 |
|------|------|------|------|
| 桌面验证 | 模拟器生成数据 | 0 | M0–M6 全程 |
| 原型车 | 成品底盘+RK3588+GPS+RGB相机+气象四件套+4G | 约1–2万 | 验证 0.5m 节拍采样 |
| 论文级 | 高离地可调轮距底盘+RTK+NDVI主动光源+激光雷达 | 10万级起 | 生产级精度 |

定位精度是分档关键：原型车 GPS 误差(2–5m)大于采样间距，需垄行编号+里程计补；论文级用 RTK(±2cm)。

### 论文级小车硬件参考规格（依据 Agronomy 13(12):3043 + 火眼金睛案例）

| 项 | 参考规格 | 来源 |
|----|----------|------|
| 底盘 | 轮式四驱、离地 85–145cm 可调、轮距可调、窄轮 7cm（不压苗） | 南农论文 |
| 动力 | 轮毂电机 480W/48V×4、60V/20Ah 续航约 3h、载荷约 15kg | 南农论文 |
| 车速 | 0.1–0.3 m/s（每 0.5m 一个点 = 1.7–5s/点，节拍匹配） | 南农论文 |
| 长势传感 | 主动光源 730/810nm 双波段 NDVI/RVI（底盘下、距冠层 40–60cm） | 南农论文 |
| 视觉 | RGB 高清相机 + 可选激光雷达 + RTK + IMU | 火眼金睛 |
| 边缘算力 | RK3588 + 轻量化 YOLO（YOLOv8Ghost 参考：7.7ms/张、86.73%） | 火眼金睛 |
| 通信 | LoRa 传天气/状态小数据 + 4G/5G 传图像，离线缓存 | Frontiers 综述 |

## 13. 风险与对策

| 风险 | 对策 |
|------|------|
| 数据模型返工 | M2 前用模拟数据验证；ORM 集中管理 |
| 采样点数据量大（一亩≈1300+点） | 分页/聚合 + PostGIS 空间索引 + 照片对象存储 |
| 占位算法演示效果差 | 用真实农田照片样本 + 真实图像统计 |
| 规则库专业性不足 | 聚焦 1–2 种作物，规则经农技资料/人员复核 |
| YOLO 精度依赖数据 | 标注回流闭环是生命线，M6 起建设 |
| LLM 幻觉/成本 | 规则兜底 + 建议可追溯 + 按需调用 |
| 硬件采购延迟 | 软件先行，M0–M6 零硬件依赖 |

## 15. 技术模块分解（v1.0，2026-08）

### 模块视图：5 大部分

| 模块 | 子模块 | 关键技术 | 负责 |
|------|--------|----------|------|
| **一、移动采集端（小车）** | 1.1 底盘行走控制；1.2 0.5m 定距采样（编码器触发）；1.3 感知（RGB+温湿光风+GPS）；1.4 边缘主控（打包/缓存）；1.5 通信（WiFi/4G） | STM32/树莓派、编码器中断、巡检包协议 | 成员A |
| **二、平台后端** | 2.1 基础管理(用户/地块/作物/设备)；2.2 数据接入(巡检包API+照片存储)；2.3 分析引擎(Analyzer接口+占位/YOLO)；2.4 评估+规则建议引擎；2.5 查询统计导出 | FastAPI、SQLAlchemy、SQLite→PostGIS | 成员B+AI |
| **三、Web 前端** | 3.1 管理页面；3.2 地图(地块/轨迹/热力)；3.3 点详情+时间轴；3.4 建议面板 | Vue3、Leaflet、ECharts | 成员B+AI |
| **四、AI 识别** | 4.1 数据集(公开+自采+标注回流)；4.2 训练(YOLOv8n/Colab)；4.3 推理服务(云端API→边缘NPU) | YOLO、标注工具 | 两人 |
| **五、仿真与验证** | 5.1 模拟数据生成器；5.2 采样密度实验；5.3 系统测试 | 规则生成、统计学 | AI+A |

### 数据流视图：6 个环节
采集（0.5m触发）→ 传输（巡检包上传）→ 存储（采样点/天气/照片）→ 分析（识别+评估）→ 决策（规则建议）→ 展示（地图/时间轴/报告）

### 依赖与里程碑映射
小车(模块一) 与 模拟器(5.1) 是同协议的双数据源 → 后端(模块二) → 前端(模块三)；算法(模块四)为后端分析引擎供能；5.2 实验为论文供数据。
M0=骨架；M1=2.1+3.1；M2=2.2；M3=2.3；M4=2.4；M5=5.1；M6=3.2–3.4；M7=模块一实装。

### 工作量占比（2人+AI）
模块一 25%（纯人工动手，AI 无法替代）；模块二+三 40%（AI 可扛大头）；模块四 20%；模块五 15%。

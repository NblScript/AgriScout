# AgriScout 开发思路与路线图（v0.1）

> 核心前提：目前没有任何硬件（开发板/小车/传感器）。
> 对策：平台开发完全不需要硬件 —— 用**模拟数据生成器**扮演小车，硬件到位后无缝替换。

## 一、四条开发原则

1. **软件先行，硬件后接**
   平台只认"数据协议"，不认"数据来源"。模拟器和真车发出完全相同格式的数据，
   平台无从区分（也不需要区分）。真车到位时只需在车上部署采集端程序。

2. **接口抽象，可替换**
   图像识别是"接口 + 占位实现"：MVP 用简单规则算法（如绿色覆盖率估计长势），
   后续换成 YOLO 轻量模型时，业务层代码零改动。建议引擎同理：先规则，后可升级 LLM。

3. **数据驱动开发**
   模拟器按真实场景生成数据：垄行、每 0.5m 采样点、坐标、天气快照、作物、生育期。
   用这份数据反过来验证平台的每个环节，开发期就能发现数据模型的问题。

4. **小步快跑，每个里程碑可演示**
   每个里程碑结束都有肉眼可见的成果，不做"憋大招"式开发。

## 二、仓库结构（monorepo）

```
AgriScout/
├── backend/               # Python FastAPI 后端
│   ├── app/
│   │   ├── api/           # 路由：地块/作物/巡检/采样点/分析/建议
│   │   ├── core/          # 配置、数据库连接、安全
│   │   ├── models/        # SQLAlchemy ORM 模型
│   │   ├── schemas/       # Pydantic 校验模型（= 数据接入协议）
│   │   ├── services/      # 业务逻辑
│   │   │   ├── analysis/  # 图像识别接口 + 占位实现
│   │   │   ├── advice/    # 规则建议引擎（规则文件可配置）
│   │   │   └── ...
│   │   └── main.py
│   ├── tests/
│   └── pyproject.toml
├── frontend/              # Vue 3 + Vite 前端
│   └── src/
│       ├── views/         # 地块管理/巡检/地图/分析/建议页面
│       ├── components/
│       └── api/           # 与后端对应的 API 封装
├── simulator/             # 模拟小车数据生成器（Python 脚本）
│   ├── generate.py        # 生成一次模拟巡田（地块、轨迹、采样点、天气）
│   └── upload.py          # 按后端 API 协议批量上传
├── docs/                  # 设计文档与调研笔记
└── docker-compose.yml     # PostgreSQL + PostGIS + 后端 + 前端一键起
```

数据库：开发期 SQLite（零配置），生产 PostgreSQL + PostGIS（空间轨迹/采样点）。
通过配置切换，代码用 SQLAlchemy 统一。

## 三、里程碑（M0–M7）

| 里程碑 | 内容 | 验收标准（可演示） |
|--------|------|--------------------|
| **M0 工程骨架** | 脚手架、配置、数据库、健康检查、前后端联通 | 打开页面看到"系统在线" |
| **M1 基础管理** | 地块/作物/种植记录 CRUD + 用户角色 | Web 界面增删改查地块和作物 |
| **M2 数据接入 API** | 巡检任务、采样点、天气数据的接收协议 | 用 curl/脚本上传一次巡田数据并查得出来 |
| **M3 分析管线** | 图像识别接口 + 占位实现 + 生长评估 | 上传一张照片，返回阶段/长势的评估结果 |
| **M4 建议引擎** | 规则库（作物×阶段×天气→农事建议） | 输入评估结果+天气，输出可追溯的农事建议 |
| **M5 模拟器** | 模拟小车生成器：0.5m 节拍、坐标、天气快照 | 一键生成一次完整模拟巡田并入库 |
| **M6 可视化** | 地块地图、巡检轨迹、采样点热力、时间轴回放、建议面板 | 在 Web 地图上完整回看一次"虚拟巡田" |
| **M7 硬件接入** | 采集端 Agent（MQTT）+ 小车端 SDK + 数据协议文档 | 真车（哪怕是树莓派+相机）发数据即入平台 |

M0–M6 完全不需要硬件；M7 才碰真设备。M6 结束时系统已是完整可用的软件产品。

## 四、关键接口设计（提前定死，避免返工）

### 1. 数据接入协议（采集端 ↔ 平台）
统一 JSON，一次上传 = 一次巡检的完整包：

```json
{
  "patrol": { "field_id": 1, "started_at": "...", "ended_at": "...",
              "device": "sim-001", "track": [[lng,lat], ...] },
  "capture_points": [
    { "seq": 12, "distance_m": 6.0, "lng": ..., "lat": ...,
      "photo": "<base64或上传后URL>", "captured_at": "...",
      "weather": { "temp_c": 26.3, "humidity_pct": 68, "light_lux": 42000,
                   "wind_mps": 1.2, "rain_mm": 0.0 } }
  ]
}
```
平台不关心 `device` 是模拟器、RK3588 小车还是树莓派。

### 2. 图像识别接口（分析管线内部）
```python
class Analyzer(Protocol):
    def analyze(self, image: bytes, context: CaptureContext) -> AnalysisResult: ...
```
- 输入：照片 + 上下文（坐标、天气、作物、生育期、NDVI 如果有）
- 输出：结构化结果（生育期概率、长势等级、病虫害风险分、检测框）
- 占位实现（MVP）：绿色覆盖率 + 简单规则 → 长势等级；病虫害风险用天气规则模拟
- 真实实现（P3）：YOLOv8 轻量模型（参考火眼金睛 YOLOv8Ghost 指标）

### 3. 建议引擎规则格式（YAML 可配置）
```yaml
- id: R-WHEAT-DROUGHT-01
  crop: 小麦
  condition: { stage: 拔节期, soil_related: true, rain_7d_mm: { lt: 5 } }
  action: 建议灌溉，亩灌水量 40–50 方
  priority: high
```
每条建议可追溯到命中的规则 id，满足"建议可解释"要求。

## 五、硬件后接时会发生什么（M7）

真车到位后，只做两件事：
1. 车上部署一个**采集端 Agent**（Python/Rust 小程序）：读相机、读传感器、
   按 0.5m 触发采样、打包成上述 JSON，通过 4G/MQTT 或回基站后批量上传
2. 平台侧**零改动**（协议早已定死）

识别模型的替换也同理：把占位 Analyzer 换成 YOLO 实现即可。

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| 数据模型设计不合理，后期改库 | M2 前用模拟数据反复验证；模型集中在 ORM 层，改动可控 |
| 0.5m 采样点数据量大（一亩地约 1300+ 点） | 采样点分页/聚合查询；照片对象存储；PostGIS 空间索引 |
| 占位算法太假，演示没说服力 | 占位实现也基于真实图像统计（颜色/纹理），演示时用真实农田照片 |
| 规则建议库内容不专业 | 先聚焦 1–2 种作物，规则请农业资料/农技员复核 |

# AgriScout（巡知）完整系统建设方案

> 目标架构版 v1.0
>
> 本方案描述项目最终要建设的完整系统结构、接口、数据闭环和验收方式，服务于小麦等大田作物的近地巡检、病害风险评估和主动学习。文中“系统”均指目标形态，具体指标以硬件联调和田间实验为准。

## 1. 系统目标

AgriScout（巡知）要建设一套由移动巡检小车、边缘 AI 主机、农田管理平台和人工复核流程组成的端—边—云协同系统。系统以 Raspberry Pi 3B 和 Jetson TX2 为现场计算基础，以统一巡检包协议连接采集端和平台，形成以下闭环：

```text
地块建档 → 任务规划 → 近地采样 → 边缘筛查 → 可靠上传
    → 异步分析 → 病害区域风险评估 → 规则建议
    → 人工复核/复巡 → 主动学习 → 模型受控发布
```

最终系统要回答四个问题：

1. 哪个观察区域出现了值得关注的异常？
2. 该异常是否正在发展，经农艺确认的预测窗口 H 内的风险如何？
3. 农技人员应该先复查哪里、采用什么视角和频率？
4. 人工复核结果如何沉淀为下一版数据集和模型？

首阶段聚焦一种作物的一种病害，输出区域级风险评估；虫情监测作为后续扩展，按目标虫害及其可观测特征选择近地 RGB、诱捕或其他专用采集方式并验证。

## 2. 设计原则

1. **端—边—云分工**：Pi 3B 负责采集、编排与软件监控，独立硬件负责急停和失联保护；场边 TX2 同时承载推理与轻量平台，云端作为扩展部署。
2. **数据先于结论**：任何风险和建议都能回到原始照片、采样时间、位置来源、质量信息和模型版本。
3. **人机协同**：模型负责筛查和排序，农技人员负责关键复核及施药、灌溉等处置确认。
4. **离线可恢复**：采集、存包、上传、分析和展示解耦；网络或服务短暂不可用不应破坏原始数据。
5. **可替换接口**：平台依赖巡检包合同，不依赖某一款相机、主控板或推理运行时。
6. **可验证指标**：采样、推理、预测、主动学习和安全运行均通过对照实验或故障注入验收。

## 3. 使用对象和场景

### 3.1 使用对象

| 角色 | 任务 |
|---|---|
| 巡检操作员 | 配置设备、加载路线、启动/暂停任务、处理安全告警 |
| 农技人员 | 查看风险图、回放图像、确认疑点、复核建议 |
| 项目管理员 | 管理地块、作物、种植批次、任务、设备和权限 |
| 算法人员 | 管理标注集、训练评估模型、发布受控版本 |

### 3.2 典型场景

- 小麦拔节至灌浆期的病害早期筛查。
- 降雨、持续高湿、干旱或大风后的重点区域复查。
- 育种试验田按小区和重复组的固定观察。
- 合作社多地块的风险优先巡检。

## 4. 总体架构

```text
┌──────────────────── 端：移动巡检小车 ────────────────────┐
│ 四驱底盘 + PWR-A53 驱动板 + Robot-Eye 摄像头 + 二自由度云台 │
│ 超声波/红外避障 + Raspberry Pi 3B + 8.4V 电池             │
│ 任务执行、运动安全、拍摄编排、协议打包、磁盘队列、状态上报 │
└──────────────────────────┬─────────────────────────────┘
                           │ 局域网 / Wi-Fi / 现场网络
                           ▼
┌──────────────────── 边：Jetson TX2 ─────────────────────┐
│ 图像质量检查、预处理、轻量模型推理、候选排序、边缘摘要     │
│ 轻量平台：API、任务、SQLite、本地照片存储、Vue 静态前端   │
│ 与 Pi 跨主机通过 HTTP 通信，推理服务经平台接口提交结果    │
└──────────────────────────┬─────────────────────────────┘
                           │ 可选：授权同步 / 扩展部署
                           ▼
┌──────────────────── 云：平台扩展（可选） ─────────────────┐
│ 接入、照片存储、异步分析、风险评估、规则建议、标注、报告   │
│ 任务/复巡、模型管理、地图、时间轴和设备监控               │
└──────────────────────────┬─────────────────────────────┘
                           ▼
                  独立训练、评估和模型发布环境
```

默认 Pi 安装在小车上，TX2 是场边局域网主机，同时承载推理服务和轻量平台，现场运行不依赖额外 PC 或公网；手机或平板浏览器访问管理页面。独立训练和评估环境可使用离线或远程算力，不是现场运行前提。推理与平台是逻辑服务划分，同机可用进程间接口或 HTTP，Pi 与 TX2 跨主机使用 HTTP。TX2 同车安装作为另行验证供电、载荷和散热的可选方案。模拟器、真车、固定监测点和其他农业装备均通过巡检包接入，不能通过导入 backend 内部模块绕过协议。

## 5. 小车硬件结构

### 5.1 设备分工

| 硬件 | 目标职责 | 设计要求 |
|---|---|---|
| Raspberry Pi 3B | 采集主控、任务编排、网络和队列 | 稳定启动、散热、可靠存储、GPIO/PWM/UART 接口 |
| PWR-A53 驱动板 | 四驱电机驱动和速度控制 | 确认供电、通信、PWM、过流和急停接口 |
| 四驱底盘 | 行间低速移动 | 低速稳定、离地间隙、轮胎不压苗、载荷可控 |
| Robot-Eye 摄像头 | 作物近地 RGB 采集 | 分辨率、帧率、弱光表现、Linux 驱动兼容 |
| 二自由度云台 | 视角调整和疑点复拍 | 角度限位、回中、拍摄时抖动控制 |
| 超声波/红外避障 | 障碍预警和安全停车 | 识别盲区、强光和叶片误触发评估 |
| 8.4V 锂电池 | 小车能源 | 保险丝、总开关、分路稳压和电量监测 |
| Jetson TX2 | 场边推理与轻量平台 | 独立电源、散热、存储、JetPack/TensorRT 适配和资源限额 |

### 5.2 供电和安全

```text
8.4V 电池
  ├─ 保险丝/总开关 → PWR-A53 与电机
  ├─ 稳压模块     → Raspberry Pi 3B
  └─ 稳压/驱动模块 → 摄像头、云台和传感器

场边独立电源（匹配具体载板输入要求） → Jetson TX2
```

小车非隔离电路按驱动要求分路供电并共地，避免电机及舵机瞬态电流导致主控掉电。默认场边 TX2 使用独立电源，不接小车电池；可选车载方案须按具体载板输入范围、峰值功率和电池放电范围设计升降压与保护，不能直接假定 8.4V 可用。

实体急停直接切断电机使能或动力回路，不经 Pi 软件转发。驱动板或独立控制器提供命令超时看门狗、失联停车及所需电机闭环；所选驱动板不具备时配置独立控制器。Pi 普通 Linux 不承担硬实时保证，仅进行编排、软监控、停车请求和事件记录。停车距离和响应时间须结合车速、载荷和场地验收，并提供低电压告警、启动自检与人工接管。避障模块是安全辅助，不替代现场监管。

### 5.3 可扩展传感器

为实现可复访观察和风险评估，硬件接口应预留轮式编码器、GPS/RTK 或标记物定位、IMU、温度、湿度、光照、风速和土壤湿度。编码器或等效里程计接入前，距离只能标记为估算值；温湿光等传感器接入前，环境字段允许为空，不能把缺失值当成实测条件。

## 6. Pi 端软件结构

### 6.1 服务模块

1. **MissionManager**：加载任务、路线、采样间距、视角、速度和有效期。
2. **SafetyController**：软件监测避障、硬件急停反馈、通信超时和低电压，请求停车并记录状态，不代替硬件安全回路。
3. **MotionController**：向驱动板或独立控制器发送速度、停车请求和周期心跳；硬件侧负责 PWM、必要闭环与命令超时保护。
4. **CameraController**：封装 Robot-Eye/UVC 相机，统一返回 JPEG 和质量信息。
5. **GimbalController**：执行任务视角、回中和疑点复拍动作。
6. **SensorCollector**：采集时间、里程、位置来源、设备状态和环境快照。
7. **CaptureScheduler**：按编码器距离或兼容的估算步长触发采样。
8. **PackageBuilder**：生成有时间范围、任务标识和序列号的巡检包。
9. **DurableSpool**：每次成功采集后立即持久化照片与点元数据，再以临时文件、刷盘和原子替换保存任务清单及待上传包。
10. **PlatformClient**：区分可重试网络/5xx/429、校验错误和待核对冲突。
11. **HealthReporter**：上报电量、温度、队列大小、采集计数和错误原因。

### 6.2 采样状态机

```text
INIT → SELF_CHECK → READY → MOVING → SAMPLE → MOVING
  │        │          │       │          │
  └────────┴──────────┴───────┴──────→ SAFE_STOP
```

任何障碍、急停、安全控制链路超时、低电压或硬件异常均进入 `SAFE_STOP`；仅上传中断时按已批准的离线策略执行或停车，不与电机命令超时混淆。硬件急停及看门狗独立生效，Pi 恢复后同步状态。采样前检查相机、云台、存储和任务有效期；采样后检查图像清晰度、时间关系和包校验值。

成功帧与元数据在下一采样周期前完成持久化确认。重启扫描任务清单、照片哈希和提交记录，恢复已保存的点，生成完整或部分巡检包；未完成写入的点记录为缺失。拍摄失败的帧不能恢复，只记录原因并按策略重拍。重拍生成新的采样记录，保留真实拍摄时间。

### 6.3 任务包

任务包括地块、种植批次、路线、采样模式、目标间距、最大速度、云台角度、安全策略、过期时间和任务版本。Pi 必须验证任务版本、设备绑定和有效期，心跳中报告执行阶段、位置来源、队列大小和异常码。

## 7. TX2 边缘推理结构

TX2 处理流水线为：

```text
图像接收 → 清晰度/曝光/遮挡检查 → 缩放与预处理
       → 作物/器官/病害模型 → 长势与异常特征
       → 不确定性/新颖度/质量评分 → 返回边缘结果
```

输出至少包含 `model_version`、输入尺寸、运行时、设备信息、检测候选、置信度、不确定性、质量标记和生成时间。TX2 上的推理服务只生成边缘摘要，经平台服务保存版本化结果，不直接改写历史记录；同机平台服务承担历史关联、风险和管理功能。训练环境和 TX2 运行环境分离，模型以与 JetPack、Python、TensorRT 版本匹配的适配层部署。

边缘与平台的职责如下：

| 任务 | 推理服务（TX2） | 平台服务（默认同机） |
|---|---|---|
| 图像质量检查 | 低延迟筛选 | 保存质量结果并统计 |
| 单图候选检测 | 可选轻量模型 | 完整模型或异步重分析 |
| 跨日期关联 | 提供摘要 | 维护历史和空间特征 |
| 风险评估 | 可输出临时分数 | 生成最终版本和证据链 |
| 断网 | 生成边缘摘要 | 网络恢复后合并原始包 |

## 8. 平台结构

### 8.1 服务分层

```text
采集端/模拟器
      ↓ HTTP 巡检包合同
API Gateway（权限、校验、错误映射）
      ↓
Ingest / Storage / Analysis / Risk / Advice / Task / Annotation / Model
      ↓
SQLite、本地内容寻址存储、持久任务表、审计日志
      ↓
Vue 管理台、地图、时间轴、风险图、报告和大屏
```

上传请求只做校验、元数据落库和照片存储；逐点识别、风险计算和建议生成通过异步任务完成。照片以 SHA-256 内容寻址保存，数据库保存 URL、哈希和元数据。规则 YAML 是规则源，运行时保存规则版本和命中快照。

默认轻量部署在 TX2 上，以持久任务表及受限并发工作进程实现可恢复异步处理，重启后恢复未完成任务；推理与平台分别设置资源限额。多地块或远程规模化部署可切换 PostgreSQL/PostGIS、对象存储和独立消息队列，业务服务与数据合同保持一致。

### 8.2 目标实体

`User`、`Organization`、`Field`、`Crop`、`Planting`、`Device`、`Mission`、`Patrol`、`CapturePoint`、`ObservationPoint`、`Media`、`WeatherSample`、`SensorQuality`、`AnalysisVersion`、`RiskPrediction`、`AdviceSnapshot`、`Annotation`、`ModelVersion`、`Evaluation`、`RuleVersion`、`DatasetVersion` 和 `DeviceEvent`。

`AnalysisVersion` 不覆盖同一点历史结果；`RiskPrediction` 保存时间窗、概率、等级、特征摘要、模型版本和置信度；`AdviceSnapshot` 保存证据、规则版本和人工状态。经标定的里程计结合固定路线起点，或标记物、可靠定位方式接入后，`ObservationPoint` 才承担跨日期复访身份。

### 9.3 目标 JSON

目标巡检包采用 `schema_version: "2.0"`；它与 URL 的 API 主版本独立。schema 查询支持版本参数并返回受支持版本。无版本的旧包仅按明确的 v1 适配规则处理，不能推断缺失的任务、定位质量或边缘结果；不支持的版本拒绝并返回升级指引，不能静默丢弃新增字段。下例是结构示例，照片 URL 指向示例资源，部署时须替换为实际可访问的内容地址。

```json
{
  "schema_version": "2.0",
  "patrol": {
    "client_package_id": "stable-id",
    "mission_id": "mission-2027-001",
    "pass_id": "pass-03",
    "field_id": 1,
    "planting_id": 2,
    "device": "rover-001",
    "started_at": "2027-04-18T08:00:00+08:00",
    "ended_at": "2027-04-18T08:12:00+08:00",
    "sampling_mode": "encoder_configured",
    "route_id": "north-row-07",
    "track": [[116.100000, 39.100000], [116.100100, 39.100000]]
  },
  "capture_points": [
    {
      "observation_key": "field-1/row-07/12.5m",
      "seq": 0,
      "distance_m": 0.0,
      "route_chainage_m": 12.5,
      "distance_source": "encoder",
      "lng": 116.1,
      "lat": 39.1,
      "position_source": "rtk",
      "captured_at": "2027-04-18T08:00:00+08:00",
      "photo": "https://media.example.org/patrols/pass-03/point-000.jpg",
      "weather": {"temp_c": 24.1, "humidity_pct": 72.0},
      "sensor_quality": {"position": "rtk_fixed", "image": "good"},
      "edge_result": {
        "model_version": "tx2-model-v1",
        "detections": [],
        "uncertainty": 0.31
      }
    }
  ]
}
```

`distance_m` 是本次巡检累计行程，`route_chainage_m` 是固定路线起点的桩号；两者可不同。编码器提供里程而非绝对经纬度，`distance_source` 与 `position_source` 独立声明；缺少有效定位时坐标允许为空，不伪造坐标。`track` 仅含有效定位点，构成线时至少两个点，单点或无定位任务不生成 LineString。

`client_package_id` 是设备范围内的幂等键，服务端同时核对包内容哈希：同键同内容返回原接收结果，同键异内容返回冲突。队列重放不能改变原始拍摄时间和点序；临时网络错误、408、425、429 和 5xx 可重试；校验错误进入人工处理；冲突响应必须核对服务端是否已接收相同包，确认前不能删除本地包。

## 10. 病害区域风险评估

### 10.1 检测与评估的区别

- **检测**：描述当前照片中出现的病斑候选、叶色变化或其他视觉线索。
- **风险评估**：结合历史、空间、生育期、环境和质量，判断观察区域在预测窗口 H 内出现或发展的概率。

H 由目标病种、作物生育期、农艺知识和观察频率共同确认，并在实验前冻结；下一巡检周期或 48 小时仅为待确认的候选窗口，不承诺适用所有病害。训练标签、特征截止时间、预测输出和验收均使用同一 H，并记录缺失复查导致的标签不确定性。

首阶段正例定义为窗口内经人工复核确认出现新病斑或达到预设严重度。输出包括风险概率、等级、趋势、影响范围、置信度、触发因素和建议复查时间。结果用于安排复查，不替代农技诊断。

### 10.2 输入特征

```text
当前视觉特征
+ 历史观察区域变化
+ 邻域聚集和传播方向
+ 作物生育期与品种
+ 温湿光、降雨和土壤条件
+ 图像清晰度、曝光、遮挡和定位质量
→ 风险概率、分级、趋势、影响范围、复查时间
```

平台按空间邻域聚合点级结果生成风险图，并保留每次聚合的时间窗、权重、阈值和模型版本。

## 11. 主动学习与复巡

主动学习流程为：

1. 计算不确定性、模型冲突、时序突变、空间孤立、新颖度和质量分数。
2. 按风险、代表性、历史覆盖和人工成本排序候选样本。
3. 生成标注任务或复巡任务，要求人工确认类别、严重度和可用性。
4. 按地块、日期和批次冻结数据集版本，训练集、验证集和测试集按地块或时间隔离。
5. 用离线指标、独立地块测试和误报漏报审查做模型发布闸门。

复巡任务可以指定观察区域、视角、路线、采样间隔和最大等待时间。模型不仅请求标注一张图，还可以请求小车从另一视角或更短间隔重新采样，使采集策略参与模型改进。

## 12. 建议与人工控制

规则引擎根据作物、生育期、环境条件、风险等级和数据质量生成建议。每条建议保存：

- 证据照片和观察区域；
- 分析版本、风险模型版本和置信度；
- 命中的规则 ID、规则版本和快照；
- 建议优先级、复查动作和人工状态。

语言模型只能用于报告表达和问答整理，不能凭空添加药剂、剂量或现场事实。施药、灌溉和大范围处置必须由农技人员确认，系统记录采纳、驳回、修改和复查结论。

## 13. 前端与用户流程

平台提供地块/作物/种植批次、设备、任务、巡检、风险、建议、标注和模型管理页面；地图显示边界、轨迹、采样点、风险热力和重点复查区；时间轴比较同一观察区域的照片、环境和风险变化；大屏展示设备状态、任务进度、地块概况和待处理告警。

用户流程为：

```text
建档 → 创建任务 → 下发设备 → 采样/上传 → 查看进度
  → 查看风险图 → 回放疑点 → 确认建议 → 标注/复巡
  → 训练评估 → 审批新模型
```

## 14. 部署、安全与可靠性

### 14.1 部署拓扑

```text
小车：Pi 3B + 相机/云台/底盘/避障/本地队列
场边主机：Jetson TX2 + 推理服务 + 轻量 API/前端/SQLite/本地照片/持久任务
网络：Wi-Fi / 4G / 5G / 局域网
可选远程扩展：PostgreSQL/PostGIS、对象存储、消息队列和云平台
训练环境（非现场运行依赖）：数据集、训练、评估和模型发布
```

### 14.2 可靠性

- 巡检包使用稳定 ID、校验值、临时文件和原子替换。
- 成功采样即时持久化；采集失败释放资源并记录缺失，保留已成功采样的数据；网络失败保留原始包并按策略重试。
- Pi、TX2 和平台均支持重启恢复、心跳、队列监控和错误告警。
- 数据库、对象存储、规则和模型均有备份与版本记录。

### 14.3 安全

设备注册凭据、TLS、角色权限、操作审计、模型发布审批和规则发布审批作为部署要求。平台允许未来接入认证系统，但采集端不得绕过协议直接写数据库。

## 15. 目标验收指标

以下指标是设计验收项，不代表未经实验的既成结果：

| 类别 | 验收目标 | 方法 |
|---|---|---|
| 采样 | 采样点有稳定包标识、时间、距离/位置来源、视角和图像质量；编码器标定后达到设定间距目标 | 标定场往返、重复采样 |
| 数据完整性 | 注入断网、超时、非 JSON、服务重启或拍摄失败后，已持久化的成功帧可重组/补传，失败帧有缺失原因及重拍记录 | 故障注入和重放测试 |
| 边缘推理 | TX2 在锁定的输入尺寸、运行时和模型版本下稳定返回结果 | 延迟、资源、温度、连续运行测试 |
| 风险评估 | 在经农艺确认的 H 窗口内，与同目标事件的单帧特征预测基线比较提前量、召回率和概率校准，数值门槛在首轮基线后冻结 | 时间切分、跨地块、消融实验 |
| 主动学习 | 相同标注预算下，与随机抽样比较有效样本比例和模型提升，数值门槛在首轮基线后冻结 | 主动/随机对照 |
| 可追溯 | 建议可回到照片、观察区域、分析/模型/规则版本和人工状态 | 随机抽查证据链 |
| 安全 | 障碍、低电压、通信超时和急停触发安全状态 | 场地故障注入 |

## 16. 实施阶段与交付物

1. **硬件安全与采样链路**：完成供电分路、急停、底盘、相机、云台、避障、任务状态机和本地队列。
2. **边缘推理与平台接入**：完成 TX2 运行时适配、巡检包接入、照片存储、异步分析和设备监控。
3. **病害风险评估**：完成一种作物一种病害的数据规范、区域标签、经农艺确认的 H 窗口预测和基线对照。
4. **主动学习与复巡**：完成候选排序、人工标注、复巡任务、数据集版本和模型发布闸门。
5. **田间验证与成果固化**：完成采样密度、视角、复查频率和主动学习对照，形成演示系统、数据集、评估报告、软件著作权、专利和论文材料。

## 17. 最终系统形态

“巡知”的最终形态是一个可在受控田间试验中反复运行的农业智能装备系统：小车在安全约束下持续采集，Pi 3B 保证数据和任务可靠，TX2 在现场完成边缘筛查，平台把多日期、多空间和多源环境信息转化为病害区域风险，农技人员通过证据链确认建议，主动学习再把高价值复核结果反馈给下一轮采集和模型训练。

系统的核心竞争力不在单独的底盘、相机或识别模型，而在于把“近地感知、风险评估、重点复查、人工确认和持续学习”组织成可重复、可解释、可扩展的完整闭环。

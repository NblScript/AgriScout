## 背景
同日第一轮审查的修复落地后复核，发现三处修复本身留下的缺陷（均已写临时用例复现）：

1. 清除任意故障注入都会把设备直接置回 `idle`，连真实急停的维护锁存也一并解除。
2. SQLite 存 `DateTime(timezone=True)` 时直接丢弃时区、不做换算；rover 与模拟器上报 `+08:00`，
   服务端默认值是 UTC。心跳乱序保护把新心跳换算成 UTC 后与库里的东八区墙钟比较，
   后续心跳全被判为「旧心跳」，设备状态再也不更新。
3. 审批修订案回写 YAML 后，冲突判断仍认为该规则「由审批产生」，此后 YAML 的正常修改被永久挡住。

另有一个回归测试用 `from tests.test_ingest import ...`，被 venv 里第三方包自带的顶层 `tests` 包遮蔽，全量 pytest 不绿。

## 决策记录
- 急停锁存来源显式化：设备管理里人工改状态写一条 `status_override` 事件（审计谁解除了锁）；
  清除故障注入时，只有「上次人工改状态之后没有真实安全事件、没有其他生效中的注入故障、也不是人工置入维护」才解锁。
- 时间统一存 UTC（D9）：`UTCDateTime` 类型在数据库边界统一换算，读回一律带 UTC 时区；
  生育期等「按天」计算用田间业务时区（东八区）取日期。旧开发库里客户端写入的东八区墙钟不做自动迁移（来源混杂无法可靠判定），演示库建议用模拟器重建。
- YAML 对齐状态落库：`rule_revisions.yaml_reconciled_at`（迁移 0013）。sync 发现 YAML 已与审批结果一致时打标，之后按正常 YAML 更新处理；`deactivate` 修订案不改内容，不参与冲突判断。

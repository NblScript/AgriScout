## 背景
本计划要在没有真实大棚数据的情况下，把 0014–0016 的闭环从头到尾跑通，并在同一份真值上比较两种巡检策略。
受模拟器红旗约束（D5）：病害规律是按设计放进模拟器的，所以**结论只能证明流程跑通，不能当作效果证据**，报告里必须写明这一点。

现有做法照搬：小麦模拟季由 `simulator/season.py` 和 `epidemic.py` 生成，导出真值 JSON；后端工具 `app.tools.replay_eval` 读真值，
调用 `services/offline_replay.py` 跑 H1–H3。本计划用同样的分工：模拟器只走 HTTP，离线比较放在后端，直接调用 0015 的 `patrol_planner`。
这样被比较的策略就是线上那一份实现，而不是另抄一份。

## 范围
- 做：大棚黄瓜模型（布局、小时环境、病害发展、可见性）；通过 API 跑通的闭环；真值导出；后端离线策略比较工具。
- 不做：真实图像识别（WP5）；对模拟参数做任何「符合实际」的声明；改动小麦模拟季。

## 设计（已定，照此实现）
1. **`simulator/greenhouse.py`**（纯模型，不做任何 IO）：
   - **布局**：设施类型 solar_greenhouse 或 plastic_tunnel，若干垄 × 若干株，每垄有株距。株号格式 `R..-P..`（见 0013 共同约定）。
   - **小时环境**：温度和湿度按日变化（正弦加噪声，用种子控制）。plastic_tunnel 的昼夜温差更大，夜间湿度更高。
     露点和湿润判定沿用 0015 的公式，在模拟器里独立实现一份（红线 6）。
   - **病害**：每株的状态按 healthy → latent → early → symptomatic 推进。
     - 每小时的感染概率 = 环境项（当时是否湿润、温度是否适宜）×（外源基数 + β × 邻株中处于 symptomatic 的株数）。
     - latent 和 early 的持续天数做成参数。
   - **可见性**：给出「检出概率」参数表，按视角（叶背 / 正面）× 时段（清晨 / 白天）× 状态分别取值。
     - 默认值示例：early 株叶背清晨 0.7、叶背白天 0.35、正面 0.1；symptomatic 株叶背 0.95、正面 0.8。
     - 另设各视角拍摄质量不合格的概率（叶背更高），以及补拍成功的概率。
     - 资料对早期病斑出现在哪一面说法不一，所以这些都必须是参数，并在注释里写明「设计假设，非实测」。
   - **真值**：输出每株每天的状态和每小时的环境。
2. **`simulator/greenhouse_run.py`**（闭环，只走 HTTP）：
   - 建大棚地块（填 `facility_type`），批量建株档案，上报环境读数（0015 的接口）。
   - 之后每天依次：
     1. 拉取计划；
     2. 按计划的株和视角生成 v2 包；合成图沿用 `photo.py` 的做法，按可见的严重度画病斑；
     3. 上传并等待分析完成；
     4. 按真值给确认名单写三阶段标注，人工误判率做成参数。
   - 结束时导出 `simulator/out/greenhouse-truth-<seed>.json`（`simulator/out/` 已在 gitignore 里）。
3. **后端离线比较**：新建 `services/greenhouse_replay.py`（纯函数）和 `tools/greenhouse_replay.py`（命令行）。读真值，逐日运行两种策略：
   - **fixed**：每 k 天全覆盖一次（每株正面和叶背各一张），不补拍，人工确认随机分配；
   - **risk**：调用 0015 的 `patrol_planner`（同一份实现，不复制）。
   - 两种策略的预算相同：每天照片数上限和人工确认数上限都一样。观测按真值和可见性参数抽样。
   - 指标：
     - 早期株首次被确认的提前量（相对于进入 symptomatic 的那天）；
     - 漏掉的株数；
     - 照片数；
     - 人工确认数，以及其中确认为健康的「无效确认」数。
   - 跑多个种子，报告均值和区间。报告输出 Markdown 和 JSON，开头写明「模拟结论只证明流程」。
4. **文档**：
   - simulator/README 增加大棚场景的用法；
   - AGENTS 命令速查加两行命令（总行数保持在 120 以内）；
   - 结论写回 0013 的「进度」，同样注明只证明流程。

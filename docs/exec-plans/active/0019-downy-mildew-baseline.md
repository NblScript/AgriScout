# 0019 · dm-cls-v1：黄瓜霜霉病识别基线（公开数据，A100 训练）

## 状态
进行中（2026-10-12）。计划 0013 WP5 里不依赖试拍的那一半：用公开数据先训「霜霉病 / 健康」基线。
用户租了 A100 服务器做模型迭代；训练在服务器上跑（Remote Control 或用户执行脚本），本仓库容器下载不了 Mendeley、也没有显卡。

## 背景
平台里每株状态（`services/plant_state.py`）的模型分现在是占位：取最近一张合格叶背图的 `risk_score`，阈值 0.4 / 0.7 是经验初值，
来源是颜色启发式，不是霜霉病模型。本计划先在来源明确的公开黄瓜叶片照片上训一个「霜霉病 / 健康」分类基线，
把数据、划分、评估、导出这条线走通，等试拍有了棚内叶背照片再微调和重定阈值。

**只能证明什么**：流程跑通；在公开的白天正面叶片照片上能否认出明显霜霉病；对其他叶部病害会不会误报。
**不能证明什么**：棚内清晨叶背上的表现、早期识别（公开数据没有「健康 / 早期 / 明显」分级）、每株状态阈值。这些写进模型说明文件的局限。

## 决策记录
- **数据（2026-10-12 核实，许可待下载时确认）**：
  - 主数据：Cucumber Disease Recognition Dataset（Mendeley，DOI 10.17632/y6d3z6f8z9.1；Sultana 等，Data in Brief 49 (2023) 109320）。
    孟加拉田间实拍，原图 1280 张、另有 6400 张增强图，8 类：霜霉病、健康叶（Fresh leaves）、炭疽病、细菌性枯萎病、蔓枯病，
    以及黄瓜果实的健康 / 腐烂 3 类。只用原图，增强图不用（我们训练时自己做增强）。
  - 可选第二来源：Cucurbit Leaf Disease Dataset（Mendeley，DOI 10.17632/whw368mjvv.1，2025）。4121 张，4 类：霜霉病、健康叶、
    卷叶病毒、花叶病毒；原图和增强图混放，没写作物是不是黄瓜。计划 0013 记的「CC BY 4.0」页面上没核实到，下载时由脚本读许可。
  - 待核实的候选：mb3vnhpk8z（「复杂环境」黄瓜叶部病害检测与分割，带标注）、Data in Brief 2024 孟加拉蔬菜叶片手机照片集（黄瓜 1626 张）。
  - 许可不是 CC BY 4.0 / CC0 时脚本停止；人工确认后用 `--accept-license` 放行，并记入清单。原始数据与产物不入库（红线 7）。
- **任务形式：整叶图像分类，不切块**。公开数据只有整图标签、没有掩膜，没法像 rust-cls 那样按病斑像素给图块打标签。
  沿用 ultralytics 分类工具链（与 rust-cls 同一套导出和推理路径），输入 224。
- **类别：霜霉病 / 健康两类**（计划 0013 的写法）。其他叶部病害不参与训练，单独留作「误报检查集」；果实类不用。
  如果误报检查集上误报率高，v2 再加「其他病害」类，这一步要和平台每株状态的 `other` 标签一起改。
- **划分按「近重复组」，不按单张**：每张图算 8 个方向（旋转 90° 倍数 × 翻转）的差值哈希，汉明距离 ≤ 4 的归为一组（跨数据集也归），
  同组不跨划分；同组里标签矛盾的整组不用并记入清单。按组分层，训练 / 验证 / 测试 = 70 / 15 / 15，固定种子。
  缩放、剪切、任意角度旋转的增强图哈希认不出来，所以第二来源要先看文件名或目录能否分出原图，分不出时在清单里标明泄漏风险。
- **评估**：测试集上的精确率、召回率、F1、ROC-AUC、PR-AUC，按来源分开报；阈值 0.5 和「验证集召回 ≥ 0.9 的最高阈值」各报一次
  （巡检是筛查，漏报比误报贵）；误报检查集上每个病害类被判成霜霉病的比例。选模型结构只看验证集，测试集最后只跑一次。
- **导出**：`export_model.py --kind dm` 导出 `dm-cls-v{N}.pt` 和同名 .json 说明（来源、许可、清单、测试指标、局限）；
  没有 eval.json 拒绝导出（与 rust-cls 同口径）。
- **平台接入另议**：后端暂不接。用正面叶片训出的模型直接给叶背照片打分、改每株状态阈值都不合适，
  看完测试结果、拿到试拍叶背照片后再定接入方式（新决策）。
